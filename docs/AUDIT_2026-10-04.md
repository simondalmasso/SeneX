## Findings

### F1 — HIGH presentation/governance: current canon files are stale

`AUD_CANON.md` and `ARQ_CANON.md` describe ORDER084/c7-era state and old resume actions. They materially conflict with current main, runtime and ORDER097.

Action on this branch: preserve them, but mark them clearly as historical and route readers to current dated status.

### F2 — MEDIUM measurement clarity: journal history and engine epoch differ

Live engine state has 4 closed positions; durable journal has 7 trades. No explicit `epoch_reset` field exists in main.

Risk: presentations and metrics can silently compare different populations.

Recommendation: add an explicit runtime/journal epoch identifier in a future behavior-changing order. This audit branch does not alter production data contracts.

### F3 — MEDIUM scientific/governance: LiveGate is not an economic authorization gate

The six existing conditions are useful operational diagnostics, and the hard PAPER lock prevents them from unlocking capital today. However the gate does not establish incremental economic edge net of costs.

Recommendation: if a future owner order designs live promotion, require a separate economic-evidence condition and prospective replication. Do not retrofit it in this presentation-only branch.

### F4 — MEDIUM experiment operations: GPTrader treatment is idle

Packets continue accumulating, but current public state still reports 0 TAKE decisions and the last run is the 2026-09-28 canary.

Consequence: no treatment sample is being generated; `INSUFFICIENT_DATA` is expected.

This audit does not enable or modify GPTrader.

### F5 — LOW/MEDIUM least-privilege hygiene: ingest token reaches the public process environment

The launcher passes `SENEX_GPTRADER_INGEST_TOKEN` into both the GPTrader sidecar and `main_real` process environment. The public app does not expose the ingest endpoint, so no public exploit was established.

Recommendation: remove unnecessary secret propagation in a dedicated, tested operational-hardening change.

### F6 — LOW maintainability: broad exception handling is common

Static census found many `except Exception` handlers, especially in research/antifragility/adapter code. Many are intentional degradation boundaries, but broad catching can hide root causes.

Recommendation: progressively narrow exceptions at authority/security boundaries while retaining fail-closed behavior. Do not mass-refactor solely for style.

### F7 — LOW presentation: legacy and production surfaces are easy to confuse

`backend/main.py`, private admin, testnet execution and the deployed `main_real.py` were not clearly distinguished at repository entry.

Action on this branch: formal README + architecture/status/audit docs.
